# Receipt cleanup and recovery

Integrated `3718bdb` atop `e9f9370`. The final independent Astra review, `run_mtvv1nz4471141f3da`, is satisfied after the parent fixes below. This supersedes the earlier shared cleanup-directory design.

## Storage review follow-up 2: journaled claims, per-operation holders, and recorded relocation

The re-review of a07e733 found four defects in the claim design. This round replaces the shared `<base>/cleanup` directory and every fallback with one recorded mechanism, all in `crates/splice-core/src/files/storage.rs`.

**Claim holder lives beside the source entry.** Removal of a Splice-owned tree creates `.splice-<transfer id>.cleanup` with `mkdirat` on the already-open parent descriptor (the Save destination for a stage, `received/` for a cache receipt), mode 0o700 and ownership verified through its own descriptor. Because the holder is a sibling of the entry, the no-replace rename into it can never cross filesystems, so the `EXDEV` in-place fallback is gone.

**The claim is journaled before the move.** The receipt journal gains `claim: { original, holder, name, dev, ino }`, written and fsynced before the rename. After the rename the claimed name is stat'ed and compared with the verified descriptor. On mismatch nothing under it is deleted: the moved entry is renamed back with no-replace and the holder removed, or if the original name is now taken, the entry stays in the holder and the error names its location while the journal keeps the claim record. Contents are then removed through the verified descriptor, the random name is unlinked inside the holder, the holder is removed, and the claim record is cleared. `load_journal` validates the record (absolute paths, holder beside the original, holder name bound to the transfer id, 32-hex claimed name).

**Recovery resumes by recorded identity.** On start, and before any other stage or receipt handling, a journal with a claim record is resumed: when the claimed entry is missing, recovery checks the original location against the recorded identity and resumes the pending move; only absence from both locations means removal completed; an entry whose dev/ino match the record is removed as above; an entry that does not match is preserved, reported on every start with "was replaced; preserved for inspection", and the record is kept so it is never inventoried as free or deleted. Nothing is deleted from a holder without a matching journaled identity.

**Clear keeps the preflight descriptor.** `clear_journal` opens the receipt once, runs preflight and the published-root identity checks on that descriptor, and hands the same descriptor to the claim, so the post-claim identity comparison is against the inspected inode. A receipt swapped between preflight and removal fails the comparison and is restored, never deleted. A relocated receipt is additionally checked against the claim's recorded dev/ino before preflight.

**Partial failure records relocation instead of renaming back.** If removal fails after the claim (for example an unreadable 0o000 directory on macOS), the remaining tree stays in the holder. For a cache receipt the journal's `directory` and `record.paths` are rewritten to the claimed location for every root whose identity is still present, so the state exposed to native consumers points at the data's real location and a later Clear or retain targets that recorded ownership. `load_journal` accepts a cache `directory` equal to the claim location, and startup inventory treats the holder as tracked so the receipt's bytes are not double-counted. The `.retained` rename and its lost ownership no longer exist.

Contract: rename and unlink remain name-based, so the identity comparison after the claim is not atomic with the rename. Every swap at the known name is either restored or preserved with its location reported, and the only remaining name-based step targets an unguessable name inside a freshly created, owner-only holder. A same-UID process that races inside that new private namespace is outside the contract. External Save trees are never walked or modified; immutable and append-only flags are never cleared.

Regressions added: a crash after the journaled claim resumes removal of a 0o555 stage by recorded identity; a claim record whose identity no longer matches is preserved and reported on every start and refuses a later Clear; a relocated cache receipt is tracked without reservation, still fails Clear on a replaced root, and clears from its recorded location; Save-stage cleanup creates and removes its private holder beside the stage; the macOS unreadable-directory case records the relocation, exposes the new paths, and clears after manual repair.

Verification on macOS: `cargo clippy -p splice-core -p splice-proto --all-targets -- -D warnings`, `cargo fmt --check`, `cargo check -p splice-daemon`, and `cargo test -p splice-core` pass (140 unit, 62 engine, six file integration and 14 network tests). Linux was not executed. No native, GUI, clipboard, input or installed-app steps were run.

On macOS, an owned directory with no owner read permission cannot be safely opened for permission repair. Cleanup reports the failure and preserves recorded ownership; restore owner read permission before retrying Clear. Readable directories without write or search permission are repaired through verified descriptors. Linux uses a verified O_PATH descriptor for unreadable directories. Immutable flags are never cleared.

The follow-up also keeps one mutable journal through recovery cleanup and propagates relocated records through the live service's Clear completion. Failure can no longer overwrite the journal with stale paths or return stale paths from a new retained lease. Tests cover crashes before and after the claim move, repeated recovery failure, and a failed Clear followed by live retention and a successful retry after permission repair.

Parent follow-up preserves a claim when its parent directory cannot be opened. Successful claim completion resets a relocated cache directory to its valid original location and clears removed paths before dropping the claim, so the journal remains loadable if a crash precedes its removal. The 34 storage tests pass, including inaccessible-parent recovery and both completed-relocation paths. The nine integrated file-transfer scenarios also pass.
